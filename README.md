# ערכת סקילים ל-SEO

שכבה שיושבת מעל הכלים הקיימים — GSC Wizard, Localo, Clarity, DataForSEO, Semrush — ועושה
את מה שהם לא עושים: מחליטה מה לשנות, כותבת את הטקסט, מבצעת באתר, מודדת אם זה עבד,
ויודעת לשחזר.

**המטרה היא ביצוע בטוח, לא עוד רשימת המלצות.**

## העיקרון

> ה-MCPs נותנים נתונים ואבחון. הסקילים נותנים החלטה, ביצוע, ואימות.

אף סקיל לא כותב קוד שמשכפל משהו שקונקטור כבר עושה טוב.

## שני החוקים שאוכפים את זה בקוד

**1. אין ממצא בלי ראיות ובלי פעולה.**
`Finding` מסרב להיווצר אם חסרים `evidence`, `action`, `baseline`, `impact_basis` או
`confidence_reason`. זו אכיפה ב-`__post_init__`, לא הנחיה סגנונית — ככה אי אפשר לכתוב
סקיל שמחזיר "כדאי לשפר את התוכן".

**2. ירידה בדירוג לא מפעילה שחזור אוטומטי.**
תקלה טכנית (500, HTML שבור, טופס מת) → שחזור אוטומטי, אבל רק אם יש גיבוי שאומת כשחזורי
ואין עריכה מקבילה. ירידה בביצועים → דוח בלבד; ירידה 28 יום אחרי שינוי היא קורלציה,
לא סיבתיות. מצב `inconclusive` קיים במפורש.

## התקנה (חד-פעמי)

```bash
git clone <repo> && cd ai-search-bot
pip install -r requirements.txt
./install.sh
```

ההתקנה מעתיקה את `seo_core` ל-`~/.claude/seo_core/`, את הסקילים ל-`~/.claude/skills/`,
ויוצרת `~/.claude/seo/` עם `.env` ו-`clients.json` — שניהם **מחוץ לריפו** ולא נדרסים בהתקנה חוזרת.

אחר כך:

1. מלא את `~/.claude/seo/.env` לפי `.env.example`
2. השלם את `~/.claude/seo/clients.json` לפי `clients.example.json`
3. הרץ כל סקיל פעם ראשונה עם `--self-check`

### סיסמת אפליקציה ל-WordPress

לכל לקוח: לוח בקרה → משתמשים → הפרופיל → Application Passwords → צור חדשה.
השם שתיתן למשתנה ב-`.env` חייב להתאים ל-`auth_env` של אותו לקוח ב-`clients.json`.

## שפה

| | |
|---|---|
| **הממשק** — SKILL.md, דוחות, פלט טרמינל | עברית |
| **התוכן שנכתב לאתר הלקוח** | לפי `content_language` של אותו לקוח |

רוב הלקוחות בארה"ב, ולכן ברירת המחדל לתוכן היא אנגלית. הבלבול בין השניים הוא איך
לקוח אמריקאי מקבל פסקה בעברית בדף השירות שלו.

## מבנה

```
seo_core/
├─ schema.py            Finding · Result · ChangeRecord
├─ log.py               פלט טרמינל, זהה לסקילים הקיימים
├─ clients.py           רישום הלקוחות
├─ secrets.py           .env + סורק דליפות
├─ sources/             GSC · GA4 · Clarity · PageSpeed · DataForSEO · crawl
├─ wp/                  REST · Gutenberg/Elementor · תוספי SEO · גיבוי · מגבלות
├─ text/                טביעת קול · טבעיות · רוחב פיקסלים
└─ change_guard/        ששת השערים ומדיניות השחזור
skills/                 כל תיקייה הופכת לסקיל מותקן
docs/trigger-map.md     מי נטען מתי — נקרא לפני הוספת סקיל
tests/                  pytest offline, בלי רשת ובלי עלות
```

## בדיקות

```bash
python3 -m pytest tests/ -q
```

הבדיקות רצות בלי רשת ובלי עלות API. מה שנבדק:

- **חוזה ה-`Finding`** — שכל ניסוח גנרי באמת נדחה
- **דירוג** — שהמרות גוברות על קליקים, ושרמת ביטחון נמוכה מקבלת הנחה
- **רישום הלקוחות** — שלקוח מוגדר חלקית מסרב להיטען
- **סודות** — שהסורק תופס סיסמה בקוד ומתעלם מקריאה תקינה מהסביבה
- **שחזור** — ש-`safe_to_auto_rollback` דורש גיבוי מאומת ואין עריכה מקבילה
- **hash** — שזיהוי עריכה מקבילה תופס גם שינוי ב-meta בלבד, ש-`modified_gmt` מפספס

בכל סקיל, בנוסף: `--self-check` לפני נגיעה בכלום, ו-`--dry-run` שמייצר תוכנית ו-diff
מלאים בלי לכתוב שום דבר.

## סטטוס

| | |
|---|---|
| ✅ תשתית | `schema` · `log` · `clients` · `secrets` · מפת טריגרים · התקנה |
| ⏳ הבא | `wp/` · `change_guard` · הפיילוט `content-decay` |
| 📋 אחר כך | `wordpress-speed-optimizer` · `wordpress-migration` · שאר הסקילים |

סדר הבנייה: תשתית → פיילוט אחד מלא → בדיקות שחזור → מהירות → מיגרציה → הרחבה.
המטרה היא להוכיח שתהליך אחד עובד בבטחה מקצה לקצה לפני שמרחיבים.
