# WordPress Migration

העברה היא הפעולה היחידה כאן שיכולה להרוס עסק בצהריים אחת. לכן היא בנויה
כמכונת מצבים: **כל שלב נרשם על הדיסק ברגע שהוא מסתיים.** ריצה שמתה באמצע
נקראת אחר כך — מה הושלם, באיזה מצב שני האתרים נמצאים, ומה הדרך החוצה.

| השלב | מה קורה | מה המצב אם זה נופל כאן |
|---|---|---|
| `preflight` | מגבלות ויכולות בשני הצדדים | אף אתר לא נגע |
| `backup` | גיבוי לשני הצדדים + אימות | אף אתר לא נגע |
| `export` | קובץ ה-wpress + שער הגודל | היעד לא נגע |
| `import` | דריסת היעד | **היעד חלקי — שחזר מגיבוי היעד** |
| `postcheck` | מה שחייב להיות נכון אחרי | ההעברה בוצעה, משהו שבור |

**כשל בזמן ייבוא הוא המקרה המסוכן.** הסקיל אומר במפורש לשחזר מגיבוי היעד ולא
לנסות ייבוא שני על גבי הראשון.

## WP-CLI קודם, דפדפן רק אם אין ברירה

הגרסה החינמית והגרסה בתשלום חושפות פקודות WP-CLI שונות, וזה השתנה בין
מהדורות. אז הסקיל **שואל את התוסף המותקן** במקום להניח:

```bash
python scripts/wp_migration.py --self-check --client example.com \
    --source-cmd "ssh old-host wp" --target-cmd "ssh new-host wp"
```

אין WP-CLI, או שאין פקודת ייבוא — הסקיל עובר למצב `browser` ומדפיס בדיוק מה
לעשות בממשק הניהול. הוא לא מנסה להכריח.

## התהליך

```bash
# 1. מגבלות אמיתיות משני הצדדים
python scripts/wp_migration.py --mode preflight --client old.com --target new.com

# 2. גיבויים — ואימות שהם לא קטועים
python scripts/wp_migration.py --mode backup --client old.com \
    --source-backup src.wpress --target-backup dst.wpress

# 3. ייצוא + שער הגודל
python scripts/wp_migration.py --mode export --client old.com --archive site.wpress

# 4. ייבוא — דורש --confirm וגם אישור מוקלד
python scripts/wp_migration.py --mode import --client old.com --confirm

# 5. בדיקות
python scripts/wp_migration.py --mode postcheck --client old.com \
    --url https://new.com/ --url https://new.com/services
```

בכל רגע: `--mode status` מציג איפה ההעברה עומדת ומה הדרך החוצה.

## שער הגודל

**500MB על הקובץ הסופי, נמדד על הקובץ עצמו** — אחרי דחיסה, לא על אומדן
לפניה. ובנוסף נבדקות המגבלות שבאמת חוסמות ביעד: `upload_max_filesize`,
`post_max_size`, המגבלה שהתוסף מציג, `memory_limit`, ושטח דיסק פנוי —
פי 2.5 מהארכיון, כי הפריסה צריכה מקום למה שיוצא ממנו.

חורג? הסקיל **קורא את הארכיון ומראה מה גדול בו** — הפורמט הוא רצף כותרות
של 4377 בתים, אז אפשר למנות את כל הקבצים בלי לפרוס כלום:

```
  9.0MB  wp-content/uploads/2024/hero.jpg
  3.0MB  ./database.sql
```

ואז עוצר. **מדיה, תוכן, משתמשים והזמנות לא נמחקים כדי להיכנס לגבול.** מה שכן
מותר להסיר: cache, גיבויים ישנים של תוספים, transients, לוגים, גרסאות ישנות
של פוסטים, וספאם. כל קטגוריה אחרת נדחית בשמה — כדי שדבר לא ייסחף בטעות
לערימת "בטוח למחיקה".

## מה זה "גיבוי מאומת"

קובץ קיים · מעל 1MB · נפתח בשם קובץ תקין · **ומסתיים בבלוק הסיום של התוסף.**
הבדיקה האחרונה תופסת קובץ שנקטע בהעברה — וכך מתחילים רוב הסיפורים על "הגיבוי
היה פגום". אימות מלא הוא שחזור בפועל, והסקיל אומר את זה במפורש ולא מתחזה.

**גיבוי לא נמחק לפני אישור סופי** — גם אחרי שהכול ירוק.

## הבדיקות שאחרי

לפי סדר העלות: **noindex שנגרר מסביבת הפיתוח** (meta או `Disallow: /`),
אזכורים שנשארו לדומיין הישן, קנוניקל שמצביע אחורה, תוכן מעורב אחרי מעבר
ל-HTTPS, טפסים שנעלמו, **CSS של Elementor שלא רוזגנר**, ותמונות שמחזירות 404
— הסימן ש-uploads לא עשה את הדרך.

רישיונות תוספים לא ניתנים לזיהוי מה-HTML, אז הם מופיעים כרשימה לבדיקה ידנית:
Elementor Pro, WP Rocket, Gravity Forms, ACF Pro, WPML ועוד.
