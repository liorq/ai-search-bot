# On-Page Optimizer

טבלת השאילתות של Search Console מכילה שלוש בעיות שונות שנראות זהה בטבלה,
ולכל אחת תיקון אחר:

| | מה קורה | התיקון |
|---|---|---|
| 🎯 `near_miss` | מיקום 4–20, הרבה הופעות | להרחיב את המענה בדף הקיים |
| 🔀 `cannibalised` | שני דפים שלנו על אותה שאילתה | **איחוד** — לא שכתוב של שניהם |
| 🕳️ `coverage_gap` | המילים של השאילתה לא בדף | סעיף חדש שעונה ישירות |
| ✏️ `low_ctr` | מיקום טוב, קליקים נמוכים | **שייך ל-`ctr-titles`** |

`low_ctr` מדווח כאן ולא מטופל כאן. כשגוגל כבר מדרג את הדף גבוה והקליקים לא
מגיעים, הבעיה בטייטל ובתיאור — שכתוב תוכן לא יעזור, והסקיל אומר את זה במקום
להציע את התיקון הלא נכון.

## עקומת ה-CTR — מהאתר עצמו

כל אומדן כאן נשען על "כמה קליקים שווה מיקום". טבלה ממוצעת מהתעשייה היא ניחוש:
שרברב מקומי ואתר השוואות עובדים על עקומות שונות לגמרי באותו מיקום.

אז העקומה **נמדדת מהנתונים של הלקוח** — חציון CTR לכל מיקום, כשיש לפחות 8
שאילתות בדלי. חציון ולא ממוצע, כי שאילתת מותג אחת במיקום 1 עם 60% מושכת
ממוצע למקום שדף שירות לא יגיע אליו לעולם.

אין מספיק נתונים → נופל לעקומה ממוצעת, **ורמת הביטחון של כל ממצא יורדת
ל-`low`** וההסבר אומר בדיוק למה.

העקומה גם נאלצת לרדת עם המיקום. מדגם אמיתי בקלות מראה שמיקום 6 מכניס יותר
ממיקום 4, ובלי תיקון זה מייצר אומדן של "לעלות מקומות ולהפסיד קליקים".

## תהליך העבודה

### שלב 1: הנתונים

**זה החלק שלך.** שלוף מ-GSC Wizard שאילתות עם הדף שדורג:

```json
{
  "property": "sc-domain:example.com",
  "range": "28d",
  "rows": [
    {"query": "spring replacement cost", "url": "https://example.com/springs",
     "clicks": 24, "impressions": 1840, "position": 8.4}
  ]
}
```

ובנוסף, לבדיקת הכיסוי — הטקסט הגלוי של כל דף:

```json
{"pages": {"https://example.com/springs": "Spring replacement in Denver..."}}
```

בלי הקובץ השני הניתוח רץ, אבל `coverage_gap` מדלג — הסקיל לא ינחש מה כתוב בדף.

### שלב 2: ניתוח

```bash
python scripts/onpage_optimizer.py --mode analyze --client example.com \
    --queries queries.json --crawl pages.json
```

### שלבים 3–5: סעיף, אישור, פרסום

```bash
python scripts/onpage_optimizer.py --mode plan --client example.com \
    --url https://example.com/services/springs \
    --after "Pricing" --heading "Broken torsion spring" --text answer.txt

python -m seo_core.change_guard.plan approve plan_ab12cd34 --dir ~/.claude/seo/data/example.com/plans
python scripts/onpage_optimizer.py --mode publish --client example.com --plan plan_ab12cd34
```

`--after` היא כותרת קיימת בדף. הסעיף החדש נכנס **אחרי הסעיף שלה כולו** ולא
מיד אחרי הכותרת — אחרת הוא חוצה לשניים תשובה קיימת. אם הכותרת לא נמצאה,
הסקיל מדפיס את רשימת הכותרות שבדף.

## דגשים חשובים

**איחוד דפים אינו אוטומטי.** להחליט איזה דף שורד, מה עובר אליו, ולאן מפנים
ב-301 — זו החלטת תוכן. הסקיל מזהה, מדרג, ואומר איזה דף מוביל לפי קליקים ואז
מיקום. הביצוע שלך.

**נטיות מילים נספרות ככיסוי.** דף שכתוב בו "springs" לא חסר את "spring",
ודף שכתוב בו "התריס" לא חסר את "תריס". בלי זה הסקיל היה מייצר ממצאים שגויים
על דפים שכבר עונים בדיוק על השאילתה.

**שאילתה מפוצלת לא מדווחת פעמיים.** אם היא כבר סומנה כקניבליזציה, היא לא
תופיע שוב כ-`near_miss` — בעיה אחת, שורה אחת.

**עלייה של 3 מקומות היא התקרה.** זה מה שעבודה על הדף עצמו משיגה; מעבר לזה
נדרשים קישורים וסמכות. מיקום 41 לא מטופל כאן, כי שכתוב לא יסגור את הפער.

**ציון ה-SEO בתוסף לא מתעדכן מעריכה דרך API.** Yoast, Rank Math ו-SEOPress
מחשבים את הציון ב-JavaScript בתוך העורך ושומרים אותו כ-meta משם — שום קריאת
REST לא מריצה את החישוב. הסייטמאפ וה-indexable כן מתעדכנים; הציון נשאר על
הגרסה הקודמת. אחרי כל פרסום הסקיל מדפיס קישור עריכה ישיר, ובסוף:

```bash
python -m seo_core.wp.seo_refresh --client example.com
```

רשימה אחת של כל הדפים ששונו וטרם נפתחו מחדש, לפי סדר. לסמן כשסיימת:
`--done chg_ab12,chg_cd34`. שינוי ששוחזר לא מופיע ברשימה.

**סף מינימלי: 50 הופעות.** מתחתיו אחוזים על מספרים קטנים הם רעש.

**פרסום חסום ללקוח שלא עבר חזרה גנרלית** של כתיבה ושחזור.
